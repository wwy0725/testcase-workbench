# 测试用例生成 Skill（功能 + 接口 + 数据库 → XMind）

## 概述

本 Skill 指导 AI 根据用户提供的需求文档（必选）和设计文档（可选），运用 8 种经典黑盒测试用例设计方法，系统化生成测试用例，最终使用 `xmind-generator` 技能生成 XMind 思维导图文件（.xmind）输出。

- **需求文档解析**：使用 `chuangtzu-skill`（庄周设计页面链接解析）技能，支持提供庄周需求文档链接即可解析；
- **设计文档解析**：使用 `forum-skill`（17work 知识库）技能，支持提供 17work 设计文档链接进行解析；
- **Excel 文档解析**：提供 `.xlsx` / `.xls` / `.csv` 文件时，使用 `excel-data-wizard` 技能解析；
- **XMind 生成**：使用 `xmind-generator` 技能提供的能力生成测试用例思维导图。

**接口测试用例与数据库验证用例仅在用户提供设计文档时生成；未提供设计文档则只生成功能测试用例。**

## 适用场景

- 用户提供 PRD/需求文档/设计文档（含庄周链接、17work 文档链接），要求生成测试用例
- 用户明确要求生成功能测试用例或接口测试用例
- 用户要求输出 XMind 格式的测试用例思维导图
- 用户提到"等价类"、"边界值"、"因果图"等测试方法论关键词并要求生成用例

## 输入文件支持

### 需求文档（必选，至少一种）

- **庄周需求文档链接**：主机名为 `chuangtzu.dc.servyou-it.com` 或 `pre-chuangtzu.dc.servyou-it.com` — 加载并使用 `chuangtzu-skill`（庄周设计页面链接解析）技能解析，获取页面目录 / Markdown / 结构化 JSON，作为需求分析依据
- **Word 文档**：`.doc` / `.docx` — 使用 Read 工具读取
- **Markdown 文档**：`.md` — 使用 Read 工具读取
- **纯文本 PRD**：用户直接粘贴的文本内容
- **图片**：`.png` / `.jpg` / `.jpeg` — 使用 Read 工具读取，分析图片中的需求信息（原型图、流程图、UI 截图等）
- **Excel 文档**：`.xlsx` / `.xls` / `.csv` — 加载并使用 `excel-data-wizard`（Excel 数据处理）技能解析，读取表格内容作为需求/用例依据

### 设计文档（可选，至少一种）

- **17work 设计文档链接**：主机名为 `17work.dc.servyou-it.com` 的链接 — 加载并使用 `forum-skill`（17work 知识库）技能解析，通过 17work CLI 动态加载操作协议并读取/下载设计文档（接口设计、API 文档、数据库设计等）
- **Markdown 文档**：`.md` — 使用 Read 工具读取，包含接口设计、API 文档、数据库设计等
- **说明**：设计文档为可选项。**仅当用户提供了设计文档时，才生成「接口测试用例」与「数据库验证用例」；未提供设计文档则只生成「功能测试用例」，不输出对应 sheet。**

## 工作流程

严格按以下步骤执行，不得跳过任何步骤：

---

### 步骤 1：读取并理解输入材料

1. 按输入类型选择解析方式：
   - **庄周需求文档链接**：加载 `chuangtzu-skill` 技能，按其流程解析链接（默认 `type=md` 获取 Markdown，需要原始结构时 `type=json`），收集需求内容
   - **17work 设计文档链接**：加载 `forum-skill` 技能，先执行 `npx -y --registry=https://npm.dc.servyou-it.com @servyou-ai/17work-cli@latest skills get core` 动态加载操作协议，再按协议读取/下载设计文档内容
   - **Excel 文档**：加载 `excel-data-wizard` 技能，使用其 `scripts/excel_ops.py read` 读取表格内容（含 sheet、字段、样例数据）
   - **本地文件（Word/Markdown/图片）**：使用 Read 工具读取
2. 对于图片格式的需求文档，使用 Read 工具查看并分析图片中的内容（UI 原型、流程图等）
3. 识别文档类型（PRD/原型图/接口文档/设计文档），明确各自的关注重点

---

### 步骤 2：需求分析

输出「需求分析结果」：

1. **功能点清单**：列出所有功能点，按模块组织
2. **接口清单**：仅当提供了设计文档时列出所有接口（从设计文档中提取），包含 URL、方法、参数；未提供设计文档则跳过此条
3. **数据库表清单**：仅当提供了设计文档时从设计文档中提取所有数据库表结构，逐表列出：
   - 表名和表注释
   - 字段名、字段类型、字段长度
   - 是否可为空（NOT NULL）
   - 默认值
   - 主键、唯一键、外键约束
   - 索引信息
   - 自增字段/时间戳字段等特殊字段
4. **业务规则**：列出关键业务规则和约束条件
5. **依赖关系**：标注功能/接口/数据表之间的依赖关系
6. **待确认事项**：列出文档中不明确或有歧义的地方

---

### 步骤 3：测试方法选择

参考 `references/testcase_methods.md`，为每个功能点和接口说明采用的设计方法及理由：

- **等价类划分法**：输入参数有取值范围或格式约束时必用
- **边界值分析法**：与等价类配合使用，覆盖上点/内点/离点
- **因果图法 + 判定表法**：多条件组合影响输出的场景
- **场景法**：多步骤业务流程
- **状态迁移法**：有状态流转的对象
- **正交实验法**：多因素多水平、全组合过大时
- **错误推测法**：基于经验补充常见易错场景，功能用例兜底覆盖（空值、超长、特殊字符、重复提交等）

---

### 步骤 4：生成功能测试用例

以 Markdown 表格输出功能测试用例，字段如下：

| 字段 | 说明 |
|------|------|
| 用例编号 | FT-模块缩写-三位序号 |
| 功能模块 | 所属模块名 |
| 测试点 | 具体测试点 |
| 设计方法 | 等价类/边界值/因果图/场景法/状态迁移/错误推测 |
| 用例类型 | 正向/逆向 |
| 优先级 | P0/P1/P2/P3 |
| 前置条件 | 执行前提 |
| 测试步骤 | 编号操作步骤 |
| 测试数据 | 具体输入值 |
| 预期结果 | 可验证的预期结果 |

**用例设计质量要求：**
- 每个功能点 ≥ 1 正向 + 2 逆向
- 有范围参数必须覆盖 5 个边界点：min、min+1、normal、max-1、max
- 有边界值必须再覆盖 min-1、max+1
- 多条件组合场景，每个判定表规则至少 1 条用例
- 业务流程，每个基本流 + 备选流路径至少 1 条用例
- 状态流转，覆盖所有合法状态转换 + 所有非法转换尝试
- 每个功能点至少补充 2 条错误推测用例，常见方向：空值/null 输入、超长字符串、特殊字符（`<>&"'/\`）、重复提交/快速连续点击、输入前后空格未 trim、剪贴板粘贴内容、输入框仅含空格

---

### 步骤 5：生成接口测试用例

**仅当用户提供了设计文档（含接口设计）时才执行本步骤。** 若用户未提供设计文档，跳过本步骤并在需求分析结果中注明"未提供设计文档，跳过接口测试用例"，且最终 XMind 中不生成「接口测试用例」sheet。

以 Markdown 表格输出接口测试用例，字段如下：

| 字段 | 说明 |
|------|------|
| 用例编号 | IT-接口名-三位序号 |
| 接口名称 | 中文名 |
| 接口路径 | URL 路径 |
| 请求方法 | GET/POST/PUT/DELETE/PATCH |
| 设计方法 | 所用设计方法 |
| 用例类型 | 正向/逆向 |
| 优先级 | P0/P1/P2/P3 |
| 请求头 | JSON |
| 请求参数 | JSON（含具体测试值） |
| 预期状态码 | 200/400/404/500 |
| 预期响应体 | JSON 结构及关键字段期望值 |

**接口用例必须覆盖：**
- 每个参数：缺省、类型错误、超长、超范围、特殊字符
- 多参数组合场景
- 业务逻辑测试（重复数据 / 关联数据不存在 / 业务规则校验）

---

### 步骤 6：生成数据库表数据验证用例

**仅当用户提供了设计文档时才执行本步骤。** 若用户未提供设计文档，跳过本步骤并注明"未提供设计文档，跳过数据库验证用例"；若提供了设计文档但不含数据库表结构信息，同样跳过并注明"设计文档未提供数据库表结构，跳过数据库验证用例"。

#### 数据库验证维度

对每个数据库表，按以下 7 个维度生成验证用例：

**D1. 表结构验证：**
- 表是否存在
- 表名是否与设计一致
- 表注释/说明是否正确

**D2. 字段存在性验证：**
- 所有设计文档中定义的字段是否存在
- 是否有多余字段（未被定义的字段）
- 字段名是否与设计一致（大小写敏感）

**D3. 字段属性验证（等价类 + 边界值）：**
- 字段类型是否与设计一致（varchar/int/datetime 等）
- 字段长度/精度是否与设计一致（varchar(64) — 64 是边界值）
- 是否可为空：NOT NULL 字段拒绝 NULL 插入；可为空字段允许 NULL
- 默认值是否生效（插入时不传该字段，检查默认值）
- 自增字段的行为验证

**D4. 约束验证：**
- **主键约束**：重复主键插入应拒绝；主键为 NULL 应拒绝
- **唯一键约束**：重复唯一键插入应拒绝；唯一键为 NULL 的行为
- **外键约束**：引用不存在的父表记录应拒绝；级联删除/更新行为验证
- **CHECK 约束**：超出 CHECK 范围的值应拒绝
- **非空约束**：等价类（NULL 作为无效等价类，非 NULL 作为有效等价类）

**D5. 字段数据完整性验证（等价类 + 边界值）：**
- **数值型字段**：正常值插入（有效等价类）、超范围插入（无效等价类）、上界/下界（边界值）、刚好超出上界/下界、负数/小数
- **字符串型字段**：正常长度（有效等价类）、超长字符串（无效等价类）、空字符串、正好等于最大长度（边界值）、正好超出 1 字符（边界值）、特殊字符（`<>&"'/\`）
- **日期时间型字段**：正常日期、超出范围日期（如 0000-00-00）、边界日期（最大值/最小值）、特殊日期（2 月 29 日等）
- **枚举型字段**：合法枚举值（有效等价类）、非法枚举值（无效等价类）、空值
- **JSON/Text 型字段**：合法 JSON、非法 JSON、超大数据量
- **布尔型字段**：true/false/NULL

**D6. 索引验证：**
- 索引是否存在（普通索引/唯一索引/联合索引）
- 索引是否覆盖设计文档中定义的字段
- 联合索引字段顺序是否正确

**D7. 数据一致性验证：**
- 事务提交后数据是否正确写入
- 事务回滚后数据是否正确回滚
- 并发写入时的数据一致性
- 大数据量批量插入的性能与完整性

#### 数据库验证用例输出格式

以 Markdown 表格输出，字段如下：

| 字段 | 说明 |
|------|------|
| 用例编号 | DT-表名-三位序号，如 DT-USER-001 |
| 表名 | 数据库表名 |
| 验证维度 | D1～D7（表结构/字段存在性/字段属性/约束/数据完整性/索引/数据一致性） |
| 验证项 | 具体验证内容 |
| 设计方法 | 等价类划分/边界值分析 |
| 用例类型 | 正向验证/逆向验证 |
| 优先级 | P0/P1/P2/P3 |
| 测试 SQL / 操作 | 具体的验证 SQL 或操作描述 |
| 预期结果 | 可验证的预期结果 |

**数据库用例设计要求：**
- 每个数据库表覆盖 D1～D7 全 7 个维度（至少各 1 条）
- 每个字段至少 1 条类型校验 + 1 条内容校验
- 每个约束至少 1 条正向验证 + 1 条逆向验证
- 有主键的表必须覆盖重复主键和 NULL 主键场景
- 有外键的表必须覆盖级联删除/更新场景

### 步骤 7：构建 XMind 大纲 Markdown

将生成的测试用例整理为 Markdown 大纲文本（**仅标题行，不含正文/表格内容**），供 `xmind-generator` 技能生成 XMind。层级规则：

| Markdown 层级 | XMind 层级 | 内容 |
|------|------|------|
| `#` | 中心主题 | `项目名称 - 测试用例` |
| `##` | sheet 分组 | `功能测试用例` / `接口测试用例` / `数据库验证用例` |
| `###` | 模块(L1) | 功能模块名 / 接口模块名 / 数据库表名 |
| `####` | 用例标题(L2) | `Pn 验证<名称>` |
| `#####` | 前置条件与步骤(L3) | 前置条件+测试数据合并条 / 步骤描述 |
| `######` | 预期结果(L4) | 预期结果描述 |

大纲示例：

```markdown
# 登录模块 - 测试用例

## 功能测试用例

### 登录功能

#### P2 验证正确账号密码登录

##### 前置条件：用户已注册且未登录　测试数据：账号 test@example.com，密码 Test@123

##### 打开登录页并输入正确账号密码

###### 预期结果：登录成功，跳转至首页

## 接口测试用例

### 登录接口

#### P1 验证登录成功

##### 前置条件：接口服务正常运行　测试数据：{"username":"test@example.com","password":"Test@123"}

##### 调用登录接口

###### 预期结果：返回 200，body 包含 token
```

**关键要求：**
- 用例标题格式固定为 `Pn 验证<名称>`：文本优先级 P1-P4（P1 最高；内部 P0→P1、P1→P2、P2→P3、P3→P4）置于最前，随后以"验证"开头；标题中**不含** FT-/IT-/DT- 前缀、不含 emoji。
- `id`（FT-xxx / IT-xxx / DT-xxx）仅作用例编号追溯，不写入大纲标题。
- **前置条件与测试数据合并为同一条** `#####` 节点（标题 `前置条件：…　测试数据：…`，全角空格分隔）。
- **步骤直接作为 `#####` 节点**（去除开头序号符号），其下一层 `######` 为预期结果；步骤与预期结果不含 emoji/符号。
- 功能用例归入 `## 功能测试用例`，接口用例归入 `## 接口测试用例`，数据库验证用例归入 `## 数据库验证用例`。
- 大纲文件为中间产物，保存到 `{workspace}/tmp/testcases_outline.md`。

---

### 步骤 8：生成 XMind 文件

加载 `xmind-generator`（XMind 思维导图生成）技能，使用其 `scripts/generate_xmind.py` 脚本将步骤 7 的大纲 Markdown 转为 XMind：

```bash
python3 {xmind_generator_dir}/scripts/generate_xmind.py \
  --md {workspace}/tmp/testcases_outline.md \
  --output {workspace}/output/测试用例.xmind \
  --sheet "测试用例"
```

其中 `{xmind_generator_dir}` 为 `xmind-generator` 技能所在目录（`.opencode/skills/xmind-generator`），`{workspace}` 为当前工作空间。**所有路径使用绝对路径。**

脚本生成的 XMind 层级如下：

```
# 项目名称 - 测试用例 (中心主题)
├── ## 功能测试用例
│   ├── ### 功能模块A
│   │   ├── #### P2 验证用例名称
│   │   │   ├── ##### 前置条件：…　测试数据：…
│   │   │   ├── ##### 步骤1描述
│   │   │   │   └── ###### 预期结果描述
│   │   │   ├── ##### 步骤2描述
│   │   │   │   └── ###### 预期结果描述
│   │   │   └── …
│   │   └── …
│   └── …
├── ## 接口测试用例
│   ├── ### 接口模块A
│   │   └── …
│   └── …
└── ## 数据库验证用例
    ├── ### 表名 (user / order / ...)
    │   ├── #### P1 验证用例名称
    │   │   ├── ##### 前置条件：…　测试数据：…
    │   │   ├── ##### 验证操作步骤/SQL
    │   │   │   └── ###### 预期结果描述
    │   │   └── …
    │   └── ...
    └── ...
```

**核验要求：**
- 确认脚本输出 `OK: <路径> (节点数=N)`，产物为有效 `.xmind` 文件；
- 最终 `.xmind` 保存到 `{workspace}/output/` 目录；
- 大纲中间文件保留在 `{workspace}/tmp/`，不放入交付目录。

### 步骤 9：覆盖率自检

XMind 生成后，输出一份简短的覆盖自检摘要：

1. 需求覆盖率（功能点/接口/数据表 → 用例数量）
2. 方法使用统计（每种方法生成用例数）
3. 用例分布（正向/逆向/数据库验证 占比，含错误推测补充用例）
4. 优先级分布（P0/P1/P2/P3 数量）

## 注意事项

1. **先分析，后生成**：不要跳过需求分析直接生成用例，否则容易遗漏功能点
2. **数据具体化**：测试数据必须给出具体值，禁止使用 "xxx" 或 "测试数据" 占位
3. **预期可验证**：预期结果必须精确可验证，避免 "系统正常" 等模糊表述
4. **用例不重复**：每条用例覆盖的场景应唯一，避免重复
5. **XMind 路径**：生成的 XMind 文件保存到 `{workspace}/output/` 目录，使用 `present_files` 展示给用户；大纲中间文件放 `{workspace}/tmp/`
