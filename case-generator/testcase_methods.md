# 测试用例设计方法论参考

## 1. 等价类划分法 (Equivalence Partitioning)

**核心思想：** 将所有可能的输入数据划分为若干个等价类，从每个等价类中选取一个具有代表性的数据进行测试。

**操作步骤：**
- 分析输入条件，划分有效等价类（符合要求的输入）和无效等价类（不符合要求的输入）
- 为每个等价类编号
- 设计测试用例，每个等价类至少覆盖 1 条用例

**适用场景：** 输入参数有明确取值范围、格式约束、集合规定、布尔值等场景。

**示例：** 年龄输入框要求 1-150 的整数
- 有效等价类：1-150 之间的整数（取 25）
- 无效等价类：小于 1（取 -5）、大于 150（取 200）、非整数（取 25.5）、非数字（取 "abc"）、为空

## 2. 边界值分析法 (Boundary Value Analysis)

**核心思想：** 大量错误发生在输入范围的边界上，因此针对边界值设计用例。

**操作步骤：**
- 确定输入条件的取值范围
- 取边界值：上点（边界值本身）、内点（边界内一个点）、离点（刚好超出边界的值）
- 标准覆盖：min、min+1、normal、max-1、max
- 健壮性补充：min-1、max+1

**适用场景：** 数值范围、字符串长度限制、数组大小、时间范围等有明确边界的场景。

## 3. 因果图法 (Cause-Effect Graphing)

**核心思想：** 分析输入条件（因）与输出结果（果）之间的逻辑关系，用图形化方式表达。

**基本关系符号：**
- 恒等（Identity）：因成立→果成立
- 非（NOT）：因成立→果不成立
- 与（AND）：多个因同时成立→果成立
- 或（OR）：任一因成立→果成立

**约束关系：**
- E（Exclusive）：条件之间互斥，最多一个为真
- I（Inclusive）：条件之间至少一个为真
- O（Only One）：条件之间有且仅有一个为真
- R（Require）：一个条件成立要求另一个也成立

**操作步骤：**
1. 分析所有输入条件和输出结果
2. 分析输入条件之间的约束关系（E/I/O/R）
3. 分析输入条件与输出结果之间的逻辑关系
4. 画出因果图
5. 将因果图转化为判定表
6. 根据判定表设计测试用例

**适用场景：** 多个输入条件之间存在逻辑组合关系的场景。

## 4. 判定表法 (Decision Table)

**核心思想：** 将复杂的逻辑关系和条件组合以表格形式呈现，每条规则对应一个测试用例。

**组成：**
- 条件桩：所有输入条件
- 动作桩：所有可能的输出动作
- 条件项：每个条件的取值组合
- 动作项：每种条件组合对应的输出动作

**操作步骤：**
1. 识别所有条件桩和动作桩
2. 列出所有条件组合（n 个条件 → 2^n 种组合）
3. 简化合并：去除不可能的组合，合并产生相同结果的组合
4. 为每种组合设计测试用例

**适用场景：** 输入条件组合较多、业务规则复杂的场景，通常由因果图转化而来。

## 5. 场景法 (Scenario Testing)

**核心思想：** 通过模拟用户在业务流程中的操作路径来设计测试用例。

**操作步骤：**
1. 绘制业务流程图，识别基本流（主路径）和备选流（分支路径）
2. 确定场景：基本流 + 每个备选流组合
3. 为每个场景设计测试用例
4. 关注端到端的完整业务流程

**适用场景：** 多步骤业务流程、有明确分支和不同路径的场景。

## 6. 状态迁移法 (State Transition)

**核心思想：** 分析系统状态以及状态之间的转换规则。

**四要素：**
- 状态：对象所处的状态
- 事件/触发：导致状态变化的事件
- 动作：状态转换时执行的操作
- 下一状态：转换后的新状态

**操作步骤：**
1. 识别所有可能的状态
2. 分析状态之间的转换规则
3. 绘制状态迁移图
4. 覆盖所有合法状态转换路径
5. 补充非法状态转换尝试

**适用场景：** 订单状态、审批流程、账号状态等具有生命周期的对象。

## 7. 正交实验法 (Orthogonal Array)

**核心思想：** 利用正交表在多因素多水平的组合中科学地筛选代表性的测试数据。

**操作步骤：**
1. 确定因素（输入条件）和水平（每个因素的取值个数）
2. 选择合适的正交表：因素数 ≥ 实际因素数，水平数 ≥ 实际水平数
3. 将因素和水平填入正交表
4. 每一行对应一个测试用例

**常用正交表：** L4(2³)、L8(2⁷)、L9(3⁴)、L16(4⁵)

**适用场景：** 多因素多水平且全组合数量过大的场景。

## 8. 错误推测法 (Error Guessing)

**核心思想：** 基于测试人员的经验和直觉推测程序中可能存在的错误，有针对性地设计测试用例。作为其他设计方法的补充，覆盖容易被遗漏的常见易错场景。

**操作步骤：**
1. 回顾已生成的等价类、边界值、因果图等用例
2. 根据经验列出可能出错但尚未覆盖的场景
3. 为每个推测场景设计具体用例

**常见测试方向（功能用例）：**
- 空值 / null 输入
- 超长字符串输入
- 特殊字符输入（`<>&"'/\` 等）
- 重复提交 / 快速连续点击
- 输入前后空格未 trim
- 剪贴板粘贴内容（含格式、隐藏字符）
- 输入框仅含空格
- 必填项仅输入空格
- 数字输入框输入前导零（如 007）
- 日期输入框输入不存在日期（如 2 月 30 日）

**适用场景：** 作为其他方法的补充，适用于功能用例的兜底覆盖。每个功能点至少补充 2 条错误推测用例。
