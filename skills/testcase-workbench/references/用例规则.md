# 用例规则（团队无关）

本文件是 testcase-workbench skill 的**用例规则权威**，抽取自项目 CLAUDE.md，供跨平台分发使用。两个 subagent（generator / supplementer）在阶段 0 加载。

> 业务知识（术语表、功能文档）不属于本 skill，由 `$BUSINESS_KNOWLEDGE_ROOT` 指向的独立知识库项目提供。

## 1. 测试用例结构硬规则（生成 + 补充都遵循）

1. **每个被测功能必须有 功能用例 + 接口用例 成对出现**
2. **功能用例的前置条件必须列出接口**——元数据块 `前置条件:` 字段用 `调用的接口:` 子项写明：
   ```
   > 优先级: P1 | 关联需求: REQ_XXX | 前置条件: 调用的接口: /api/itcrmweb/follow/saveFollowRecord、/api/itcrmweb/contact/getNotRelationCallRecord | 测试数据: ...
   ```
3. **接口用例不区分新增/修改**——H5 标题用接口中文名，不加前后缀，**不写**"本期新增/改造"等时间标记
4. **新增接口的 URL 本身是一条优先级 3 用例**——形式 `查询 {完整URL}`，仅用于反查接口所属模块归属，无实际业务含义
   - 这条用例必须带 4 字段元数据 + priority-3 marker（补充场景不强制加元数据的唯一例外）
5. **功能用例的前置条件子节点用 `flag-red`（红旗）标记**——不在 notes 里写"前置条件: xxx"文字。接口用例不需要 flag-red。

**Markdown 标题层级**（XMind 兼容性硬性要求）：
```
H1 团队名（如"代账合规"）→ XMind 根节点
H2 迭代名（如"代账合规8月迭代"）→ XMind 画布标题
H3 日期（如 20260827）→ 一级节点
H4 【模块名】需求名称（**必填**，不可省略）
H5 功能点（必带元数据块）
  - 条件/场景（bullet）
    - 预期结果（nested bullet，缩进 2 空格）← 这是"H6"，用 nested bullet 表示
```

**预期结果格式**：
- 使用 **nested bullet**（`  - 预期结果`），**不使用 H6 标题**
- 条件/场景作为一级 bullet（`- `），预期结果作为其嵌套子项
- 原因：md2xmind.py 将 nested bullet 转为 XMind 子节点，视觉上条件与结果成组

**条件 vs 结果的判断**（易错点）：
- **条件 = 测试人员执行的操作或设置的场景**（如"点击按钮"、"查看卡片"、"接口返回空"）
- **结果 = 操作后可验证的现象**（如"页面跳转"、"文案展示"、"弹窗打开"）
- 同一操作下的多个观察维度合并为一个条件，多个预期结果作为其子项
- **反模式**：把"卡片名称"、"卡片文案"、"卡片样式"拆成三个独立的条件→结果对（错误）
- **判断方法**：问自己"这是测试人员要做的操作吗？" → 是=条件，是观察到的现象=结果

**命名**：测试点与测试用例的 `{需求名称}-{序号}` 必须一一对应。

## 2. 优先级规则（P1-P4，按执行要求区分）

| 优先级 | 含义 | 适用场景 | 执行要求 |
|---|---|---|---|
| **P1** | 阻塞性场景 | 核心主流程必经节点 / 关键数据正确性 / 一旦错就影响全局 | 冒烟必含、回归必跑 |
| **P2** | 重要功能 | 正常业务场景 / 主要功能路径 / 业务规则正例 | 正常回归必跑 |
| **P3** | 辅助功能 | 排序 / 搜索 / 标签 / 导出 / 头部信息 / 提示文案 / Excel 格式 / 新接口 URL 反查 | 按需测试 |
| **P4** | 极端场景 | 空列表 / null 值 / 极端输入 / 极少触发场景 | 有时间再测 |

**四步判断流程**：
1. 是否阻塞性 / 核心流程必经？→ **P1**
2. 是否重要功能 / 正常业务场景？→ **P2**
3. 是否辅助功能 / 边界场景？→ **P3**
4. 是否极端场景 / 极少触发？→ **P4**

**反模式**：
- ❌ 全部用例标 P1 → 没有分层，回归跑不动
- ❌ 头部信息 / 提示文案标 P1 → 归 P3
- ❌ 导出 / 排序标 P1/P2 → 归 P3
- ❌ P4 写成正常功能 → P4 只写极端场景（空列表/null/极端输入）
- ❌ 用"用户重要程度"判断 → 应该用"执行要求"判断

## 5. 测试设计方法（8 种，**生成时选方法、补充时查遗漏**）

生成测试用例时**必须**为每个功能点/接口选择对应的黑盒设计方法，并在"预期结果"的设计中体现方法特征。补充优化时用方法清单对照原 XMind，判断是否遗漏某类场景。

### 方法速查表

| 方法 | 核心思想（一句话） | 适用场景 | 何时选用 |
|---|---|---|---|
| **等价类划分** | 把输入分成有效/无效等价类，每类取代表值 | 输入有取值范围/格式约束/枚举集合 | 有明确输入域时**必用**，是其他方法的基础 |
| **边界值分析** | 错误集中在边界，专测边界值 | 数值范围、字符串长度、数组大小、时间区间 | 与等价类**配合用**，覆盖上点/内点/离点 |
| **因果图法** | 分析输入条件（因）与输出（果）的逻辑关系 | 多条件组合影响输出 | 多条件组合场景，画图后转判定表 |
| **判定表法** | 条件组合 → 动作映射成表，每规则一条用例 | 业务规则复杂、条件组合多 | 由因果图转化，每条规则至少 1 条用例 |
| **场景法** | 模拟用户业务路径，基本流 + 备选流 | 多步骤业务流程、端到端 | 有完整业务流程时必用 |
| **状态迁移法** | 分析对象状态及转换规则 | 有生命周期的对象（订单/审批/账号） | 有状态流转时必用 |
| **正交实验法** | 用正交表科学筛选代表性组合 | 多因素多水平、全组合过大 | 全组合数过大时用，降低用例数 |
| **错误推测法** | 基于经验推测易错场景，兜底补充 | 作为其他方法的补充 | **每个功能点必补**，至少 2 条 |

### 方法选择决策树

按输入特征选方法，**自上而下匹配，命中即用**：

```
1. 输入有取值范围/格式约束？
   └─ 是 → 等价类划分（必用）+ 边界值分析（配合）
2. 多个输入条件组合影响输出？
   └─ 是 → 因果图法 → 转判定表法
3. 是多步骤业务流程（端到端）？
   └─ 是 → 场景法（基本流 + 备选流）
4. 对象有状态流转/生命周期？
   └─ 是 → 状态迁移法（合法转换 + 非法转换尝试）
5. 多因素多水平，全组合过大？
   └─ 是 → 正交实验法（选合适正交表）
6. 以上都用过后兜底补充
   └─ 错误推测法（每功能点至少 2 条）
```

> 一个功能点常**同时命中多种方法**（如"列表页"既有输入筛选→等价类+边界值，又有业务流程→场景法）。多种方法叠加覆盖，不互斥。

### 各方法操作要点

**1. 等价类划分法**
- 划分有效等价类（符合要求）和无效等价类（不符合），每类编号
- 每个等价类至少 1 条用例
- 示例：类型字段有 5 种枚举值 → 有效等价类各取 1 条；无效等价类取"未配置的类型码"

**2. 边界值分析法**
- 标准覆盖 5 点：`min`、`min+1`、`normal`、`max-1`、`max`
- 健壮性补充：`min-1`、`max+1`（离点）
- 示例：列表每页 20 条 → 测 1 条（min）、2 条（min+1）、20 条（max）、21 条（max+1 触发分页）

**3. 因果图法**
- 分析因（输入条件）与果（输出结果）的逻辑关系：恒等/非/与/或
- 约束关系：E（互斥）/ I（至少一个）/ O（有且仅有一个）/ R（要求）
- 画因果图 → 转判定表

**4. 判定表法**
- 条件桩（所有输入条件）+ 动作桩（所有输出动作）
- n 个条件 → 2ⁿ 种组合，简化合并不可能/同结果的组合
- 每条规则至少 1 条用例
- 示例：某展示规则 = "接口返回 > 0" + "用户有查看权限" + "未到失效时间" → 3 条件 8 组合，合并后每规则 1 条用例

**5. 场景法**
- 识别基本流（主路径）和备选流（分支路径）
- 每个基本流 + 每个备选流组合至少 1 条用例
- 示例：记录保存 → 基本流（正常保存成功）；备选流（关联数据不存在→报错、必填项为空→校验提示、重复提交→去重处理）

**6. 状态迁移法**
- 四要素：状态 / 事件触发 / 动作 / 下一状态
- 覆盖所有合法状态转换 + 所有非法转换尝试
- 示例：商机状态（新建→跟进中→已成交/已流失）→ 测每个合法转换 + 非法跳转（新建直接到已成交应拒绝）

**7. 正交实验法**
- 确定因素（输入条件）和水平（每因素取值数）
- 选正交表：L4(2³)、L8(2⁷)、L9(3⁴)、L16(4⁵)
- 每行一条用例
- 示例：列表筛选有 4 个条件（对象类型/时间范围/方式/负责人）各 3 水平 → 全组合 81 条，用 L9(3⁴) 降到 9 条

**8. 错误推测法**
- 作为其他方法的补充，基于经验推测易错场景
- **每个功能点至少补 2 条**

### 错误推测常见方向

> 以下方向是常见易错场景，**不是穷举**，按功能点相关性选取：

| 方向 | 示例 |
|---|---|
| 空值/null 输入 | 必填项输入空字符串/null → 接口报错或前端拦截 |
| 超长字符串 | 文本输入超长内容 → 是否截断/报错 |
| 特殊字符 | 输入含 `<>&"'/\` → 是否转义、是否 XSS |
| 重复提交/快速连续点击 | 保存时连点保存按钮 → 是否生成重复记录 |
| 输入前后空格未 trim | 名称前后带空格 → 是否自动 trim |
| 输入框仅含空格 | 必填项仅输入空格 → 是否视为空值拦截 |
| 剪贴板粘贴 | 从 Excel 粘贴含隐藏字符/格式 → 是否清理 |
| 接口返回空导致兜底 | 列表接口返回空 → 是否展示兜底卡片/空状态 |
| 枚举值越界 | 类型字段传未配置的码值 → 是否报错 |
| 关联数据不存在 | 关联已删除的数据 → 是否报错或友好提示 |

### 方法与优先级的映射

设计用例时，**方法选用的场景特征**辅助判断优先级（与「优先级规则」四步流程叠加使用，不替代）：

| 方法产生的用例类型 | 倾向优先级 | 说明 |
|---|---|---|
| 场景法 — 基本流（主路径） | **P1** | 核心流程必经，阻塞场景 |
| 等价类 — 有效等价类正例 | **P2** | 正常业务场景 |
| 边界值 — 上点/内点 | **P2** | 正常范围内的重要功能 |
| 判定表 — 合法组合规则 | **P2** | 业务规则正例 |
| 状态迁移 — 合法转换 | **P2** | 正常状态流转 |
| 边界值 — 离点（min-1/max+1） | **P3/P4** | 边界外场景，按触发频率定 |
| 判定表 — 非法组合/异常规则 | **P3** | 异常但非极端 |
| 正交实验 — 代表性组合 | **P3** | 辅助覆盖组合场景 |
| 错误推测 — 空值/null/极端输入 | **P4** | 极端场景，极少触发 |
| 状态迁移 — 非法转换尝试 | **P3/P4** | 非法跳转，按影响定 |

> 这是**倾向**不是绝对——最终优先级以「优先级规则」四步判断流程为准，本表只辅助"看到某类用例时心里有数"。

## 6. 格式规范

**默认风格：画布 2（按业务需求/迭代组织）**
- H3 业务需求标题以 `【模块名】` 开头
- 用户明确说"按功能模块全量沉淀"时才用画布 1 风格
- 元数据块**强制**：`> 优先级: P1/P2/P3/P4 | 关联需求: ... | 前置条件: ... | 测试数据: ...`（4 字段全填）

**模块拆分原则**：
- 简单需求：少拆（深度 4-5 层）
- 复杂需求：按需拆（满足任一：多模块/多角色/多平台/多 API → 拆出独立模块）
- 反模式：每个 H4 下仅 1-2 用例（拆太碎）/ 同一功能在多 H4 重复（应合并）

**补充场景特有规则**（supplementer 用）：
- 不强制加 4 字段元数据块——若原 XMind 没用，补充时也不用
- 优先改写现有 H5 细节，少开新 H5——新信息作为现有 H5 的子项追加
- 穷举类内容只列最有代表性的 2-3 个
- 保留内联代码块/配置块原样，不要"清理"

## 7. 用例生成后检查（生成 + 补充都必须执行）

每次生成或更新用例后，对最终 Markdown + XMind 执行一轮自检：

### 检查项
1. **内容正确性**：接口 URL/字段名/枚举值与需求快照一致，禁止臆测；覆盖需求所有分支；预期结果是"预期"而非操作步骤
2. **格式规范**：标题层级完整（H1→H2→H3→H4→H5），H4 必填；每个 H5 必须带 4 字段元数据块；功能用例前置条件含 `调用的接口:`；接口 H5 用中文名不加时间标记
3. **优先级合理性**：按四步判断逐条验证，禁止全量 P1 或全量 P3，必须分层
4. **测试点完整性**：逐条比对需求/设计稿，每个功能点/接口/业务规则都有对应 H5；**功能用例 + 接口用例成对出现**；补充场景确认新设计引入的功能点全部有节点落地

### 输出要求
- 自检通过 → 输出成品（Markdown + XMind）
- 自检发现问题 → 先修复、复检通过后再输出，并在最终回复里简短报告修了什么
