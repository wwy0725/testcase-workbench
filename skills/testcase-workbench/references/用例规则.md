# 用例规则（团队无关）

本文件是 testcase-workbench 的**用例细则唯一权威**：各方法操作要点与反模式、错误推测常见方向、方法与优先级映射、生成后检查清单、教训实例（错题本）**只在这里维护**（项目 CLAUDE.md 只留指针）；同时作为 skill 的跨平台规则副本，携带结构硬规则、优先级规则、格式规范、方法速查表与决策树（这几章权威在 CLAUDE.md，改后同步过来）。两个 subagent（generator / supplementer）在阶段 0 **必读**本文件。

> 业务知识（术语表、功能文档）不属于本 skill，由 `$BUSINESS_KNOWLEDGE_ROOT` 指向的独立知识库项目提供。

## 1. 测试用例结构硬规则（生成 + 补充都遵循）

1. **材料涉及接口时，每个被测功能必须有 功能用例 + 接口用例 成对出现；材料不涉及接口时不写接口用例**——判断依据：需求材料含 Walle 接口文档、或需求正文明确给出接口 URL/字段 → 视为涉及接口，按成对规则出；否则只出功能用例，**不臆造接口用例、不在功能用例里臆测标注接口**（前置条件不写"调用的接口"、测试数据不臆测接口字段）。**接口用例归属**：接口用例不并入业务模块，统一放在名为「接口」的固定模块下——H3「接口」→ H4 接口中文名称（每个接口一个节点）→ H5 接口用例（带元数据块）；结构参考 `用例参考.xmind`（其 http/dubbo 协议分组层级比生成产物深，生成时不加协议层）
2. **前置条件按需添加，只写执行前需单独准备的业务前提**——数据/造数准备（数据存在性，如"往来对账列表存在多条不同账龄的往来单位"）、配置状态（授权/会员/白名单、角色配置、功能开关、已命中卡片）、业务逻辑依赖（如"客户已存在未读跟进记录"、"商机处于跟进中状态"、"票家家授权有效"）。**不写三类废话性前提**：① **通用背景类**——任何用例都适用的泛化操作或整份用例通用的开通/入口大前提（"已登录账号""进入首页""机构已开通某产品/端""账号可进入某页面"），它们是所有用例的默认背景，写出来只稀释有区分度的前提；② **动作状态类**——本用例步骤顺手就能产生的中间状态（"提示气泡处于展开状态""已在列表选择某排序""已切换到某页签"），这是步骤不是前置，并入条件 bullet（如"气泡展开状态下切换排序项"）；③ **具体值复述类**——具体输入值/参数/账号，归测试数据，前置条件只写数据形态。**判断口诀**：执行前需单独准备 → `前置条件:`；本用例步骤顺手可做 → 写进条件 bullet；任何用例都适用 → 不写。**与测试数据的分工**：前置条件描述数据形态/状态要求（"存在多条账龄区间不同的往来单位"），测试数据给具体值与造数指引（"3年以上/近2年/1年以内，造数见…"）——两者并存不算重复，是要求与实例的关系；业务前提信息必须在 前置条件/测试数据/用例正文 之一体现，**不能哪都没有**。元数据块 `前置条件:` 字段非必填，无前置条件时省略整个字段。知道所调用接口时用 `调用的接口:` 子项写明；**不知道接口时不捏造、不占位**接口前置条件（不写"调用的接口: 待补充"之类占位符），但可写其他业务前提：
   ```
   > 优先级: P1 | 关联需求: REQ_XXX | 前置条件: 调用的接口: /api/itcrmweb/follow/saveFollowRecord、/api/itcrmweb/contact/getNotRelationCallRecord | 测试数据: ...
   ```
   无前置条件时省略该字段：`> 优先级: P1 | 关联需求: REQ_XXX | 测试数据: ...`
3. **接口用例不区分新增/修改**——用例标题用接口中文名，不加前后缀，**不写**"本期新增/改造"等时间标记
4. **新增接口的 URL 本身是一条优先级 3 用例**——形式 `查询 {完整URL}`，仅用于反查接口所属模块归属，无实际业务含义
   - 这条用例必须带 4 字段元数据 + priority-3 marker（补充场景不强制加元数据的唯一例外）
5. **有前置条件时，用例的前置条件子节点用 `flag-red`（红旗）标记**——不在 notes 里写"前置条件: xxx"文字。无前置条件则不加；功能用例和接口用例统一处理，不按标题猜测用例类型。
6. **用例标题必须是"动作 + 预期结果"的完整句**——只写动作（如"传参指定默认账号类型为机构账号"）或名词短语（如"XX映射判定表"）不是完整用例标题，看标题不知道要验证什么；正确示例："传参指定默认账号类型为机构账号时默认展示机构账号管理"。模块/子模块容器标题不受此约束。

**Markdown 标题层级**（XMind 兼容性硬性要求）：
```
H1 当前迭代（如"代账合规8月迭代"，日期并入迭代名，不单列层级）→ XMind 根节点
H2 需求名称（必填）→ 一级节点
H3 模块名 或 用例（需求简单、不拆模块时直接挂用例）
H4 子模块名 或 用例（拆了模块、不拆子模块时用例在这层）
H5 用例（拆了模块+子模块时用例在这层）
  - 条件/场景（bullet）
    - 预期结果（nested bullet，缩进 2 空格）
  - 前置条件描述（flag-red 子节点，按需添加；功能/接口用例统一）
```

**用例层级识别**：用例不一定固定在某一层——**判断依据是标题后紧跟 `> 优先级:` 元数据块**（不管 H3/H4/H5）。模块/子模块标题后无元数据块，是分组容器。

**模块按需拆分原则**（三档，避免滥用）：
| 复杂度 | 拆分方式 | 用例落地层 | 适用场景 |
|---|---|---|---|
| 简单 | 不拆模块 | H3（直接用例） | 单一功能、无多模块/多角色/多平台 |
| 中等 | 拆一层模块 | H4（模块下的用例） | 多模块但每模块内部结构简单 |
| 复杂 | 拆模块+子模块 | H5（子模块下的用例） | 多模块且模块内部还有子结构（如"列表页"下分"筛选/列表/批量操作"）/ 需求天然有 ≥2 个并列顶层分组（多页面、多角色、多子系统），分组作 H3 容器、组内再拆 H4 子模块、用例落 H5 |
- **反模式**：每个模块下仅 1-2 用例（拆太碎）/ 同一功能在多模块重复（应合并）/ 简单需求强行拆模块（直接 H3 用例即可）/ **用"功能用例"等用例类型标签作 H3 分组容器**（用例类型不承载业务语义，应按业务模块组织或简单需求直接 H3 挂用例；**接口用例例外**——涉及接口时统一放固定命名的「接口」模块下，结构见硬规则 1，不算类型标签滥用）/ **把并列顶层分组（页面/角色/子系统）压进模块名前缀**（如"应用-顶部导航栏"、"我的-全局信息"）——应把分组上升为 H3 容器，分组内再按需拆 H4 子模块、H5 用例
- **用例绝不超过 H5**：条件/结果/前置条件一律用 nested bullet 表示，不再下沉到 H6

**预期结果格式**：
- 使用 **nested bullet**（`  - 预期结果`），**不使用标题**（条件/结果/前置条件一律用 bullet，避免用例层级超过 H5）
- 条件/场景作为一级 bullet（`- `），预期结果作为其嵌套子项
- 原因：md2xmind.py 将 nested bullet 转为 XMind 子节点，视觉上条件与结果成组

**条件 vs 结果的判断**（易错点）：
- **条件 = 测试人员执行的操作或设置的场景**（如"点击按钮"、"查看卡片"、"接口返回空"）
- **结果 = 操作后可验证的现象**（如"页面跳转"、"文案展示"、"弹窗打开"）
- 同一操作下的多个观察维度合并为一个条件，多个预期结果作为其子项
- **反模式**：把"卡片名称"、"卡片文案"、"卡片样式"拆成三个独立的条件→结果对（错误）
- **判断方法**：问自己"这是测试人员要做的操作吗？" → 是=条件，是观察到的现象=结果

**命名**：测试点与测试用例的 `{需求名称}-{序号}` 必须一一对应。

## 2. 优先级规则（P1-P4，按执行要求区分）

| 优先级 | 含义 | 适用场景 | 执行要求 |
|---|---|---|---|
| **P1** | 阻塞性场景 | 核心主流程必经节点 / 关键数据正确性 / 一旦错就影响全局 | 冒烟必含、回归必跑 |
| **P2** | 重要功能 | 正常业务场景 / 主要功能路径 / 业务规则正例 | 正常回归必跑 |
| **P3** | 辅助功能 | 排序 / 搜索 / 标签 / 导出 / 头部信息 / 提示文案 / Excel 格式 / 新接口 URL 反查 | 按需测试 |
| **P4** | 极端场景 | 空列表 / null 值 / 极端输入 / 极少触发场景 | 有时间再测 |

**四步判断流程**：
1. 是否阻塞性 / 核心流程必经？→ **P1**
2. 是否重要功能 / 正常业务场景？→ **P2**
3. 是否辅助功能 / 边界场景？→ **P3**
4. 是否极端场景 / 极少触发？→ **P4**

**反模式**：
- ❌ 全部用例标 P1 → 没有分层，回归跑不动
- ❌ 头部信息 / 提示文案标 P1 → 归 P3
- ❌ 导出 / 排序标 P1/P2 → 归 P3
- ❌ P4 写成正常功能 → P4 只写极端场景（空列表/null/极端输入）
- ❌ 用"用户重要程度"判断 → 应该用"执行要求"判断

## 3. 测试设计方法（8 种，**生成时选方法、补充时查遗漏**）

生成测试用例时**必须**为每个功能点/接口选择对应的黑盒设计方法，并在"预期结果"的设计中体现方法特征。补充优化时用方法清单对照原 XMind，判断是否遗漏某类场景。

### 方法速查表

| 方法 | 核心思想（一句话） | 适用场景 | 何时选用 |
|---|---|---|---|
| **等价类划分** | 把输入分成有效/无效等价类，每类取代表值 | 输入有取值范围/格式约束/枚举集合 | 有明确输入域时**必用**，是其他方法的基础 |
| **边界值分析** | 错误集中在边界，专测边界值 | 数值范围、字符串长度、数组大小、时间区间 | 与等价类**配合用**，覆盖上点/内点/离点 |
| **因果图法** | 分析输入条件（因）与输出（果）的逻辑关系 | 多条件组合影响输出 | 多条件组合场景，画图后转判定表 |
| **判定表法** | 条件组合 → 动作映射成表，每规则一条用例 | 业务规则复杂、条件组合多 | 由因果图转化，每条规则至少 1 条用例 |
| **场景法** | 模拟用户业务路径，基本流 + 备选流 | 多步骤业务流程、端到端 | 有完整业务流程时必用 |
| **状态迁移法** | 分析对象状态及转换规则 | 有生命周期的对象（订单/审批/账号） | 有状态流转时必用 |
| **正交实验法** | 用正交表科学筛选代表性组合 | 多因素多水平、全组合过大 | 全组合数过大时用，降低用例数 |
| **错误推测法** | 基于经验推测易错场景，兜底补充 | 作为其他方法的补充 | **每个功能点必补**，至少 2 条 |

### 方法选择决策树

按输入特征选方法，**自上而下匹配，命中即用**：

```
1. 输入有取值范围/格式约束？
   └─ 是 → 等价类划分（必用）+ 边界值分析（配合）
2. 多个输入条件组合影响输出？
   └─ 是 → 因果图法 → 转判定表法
3. 是多步骤业务流程（端到端）？
   └─ 是 → 场景法（基本流 + 备选流）
4. 对象有状态流转/生命周期？
   └─ 是 → 状态迁移法（合法转换 + 非法转换尝试）
5. 多因素多水平，全组合过大？
   └─ 是 → 正交实验法（选合适正交表）
6. 以上都用过后兜底补充
   └─ 错误推测法（每功能点至少 2 条）
```

> 一个功能点常**同时命中多种方法**（如"列表页"既有输入筛选→等价类+边界值，又有业务流程→场景法）。多种方法叠加覆盖，不互斥。

### 各方法操作要点

**1. 等价类划分法**
- 划分有效等价类（符合要求）和无效等价类（不符合），每类编号
- 每个等价类至少 1 条用例
- 示例：类型字段有 5 种枚举值 → 有效等价类各取 1 条；无效等价类取"未配置的类型码"

**2. 边界值分析法**
- 标准覆盖 5 点：`min`、`min+1`、`normal`、`max-1`、`max`
- 健壮性补充：`min-1`、`max+1`（离点）
- 示例：列表每页 20 条 → 测 1 条（min）、2 条（min+1）、20 条（max）、21 条（max+1 触发分页）

**3. 因果图法**
- 分析因（输入条件）与果（输出结果）的逻辑关系：恒等/非/与/或
- 约束关系：E（互斥）/ I（至少一个）/ O（有且仅有一个）/ R（要求）
- 画因果图 → 转判定表

**4. 判定表法**
- 条件桩（所有输入条件）+ 动作桩（所有输出动作）
- n 个条件 → 2ⁿ 种组合，简化合并不可能/同结果的组合
- 每条规则至少 1 条用例
- **先全组合、后删除（硬流程）**：维度识别（见下条）→ 先拉出**全组合表**（各维度所有水平全交叉，不跳格）→ 在表上**逐格标注去留**：保留 / 可合并（写明合并到哪格）/ 删除（写明理由：不可能出现、已被其他用例覆盖、明确不测）→ 只为保留格出用例。**禁止跳过拉表直接挑正例格**——覆盖是默认态，不覆盖才需要理由；负向格与非目标人群/端的交叉格必须出现在表上被显式确认过。全组合数过大时转正交实验法（也是一种显式简化，须记录代表性覆盖理由）
- **维度识别防漏清单**（不是穷举，逐项过一遍）：人群 / 端 / 开关 / 状态 / 角色权限 / 条件的正反两分支 / 字段取值与进入途径（见下条）/ **联动逻辑作用域**——同一联动逻辑（如“手机号→EIAM→姓名回显”）用到几个模块/入口，全组合表就在几个模块各拉一遍，禁止只在首次出现的模块拉
- **禁止对称反推**：需求材料只写明某条件的一个分支时，不得按对称/类比逻辑反推另一分支的行为——须回查设计稿/最终版材料找真实规则；找不到时把该分支标「待确认」向需求方澄清，不得假设填空（例：需求只写「隐藏入口→不发短信」，不得反推「展示→必发」——实际可能按页面内勾选项控制，默认勾选）
- **字段取值途径也是条件维度**：字段联动类功能（A 字段值触发 B 字段回显/计算），A 的取值/进入途径（手工输入 / 系统带出 / 接口回填 / 预填）本身就是一个条件维度——需求只描述其中一个途径时，其余途径须逐一确认是否走同一逻辑，默认相同而无材料支撑即违反上一条「禁止对称反推」
- 示例：某展示规则 = "接口返回 > 0" + "用户有查看权限" + "未到失效时间" → 3 条件 8 组合，合并后每规则 1 条用例

**5. 场景法**
- 识别基本流（主路径）和备选流（分支路径）
- 每个基本流 + 每个备选流组合至少 1 条用例
- 示例：记录保存 → 基本流（正常保存成功）；备选流（关联数据不存在→报错、必填项为空→校验提示、重复提交→去重处理）

**6. 状态迁移法**
- 四要素：状态 / 事件触发 / 动作 / 下一状态
- 覆盖所有合法状态转换 + 所有非法转换尝试
- 示例：商机状态（新建→跟进中→已成交/已流失）→ 测每个合法转换 + 非法跳转（新建直接到已成交应拒绝）

**7. 正交实验法**
- 确定因素（输入条件）和水平（每因素取值数）
- 选正交表：L4(2³)、L8(2⁷)、L9(3⁴)、L16(4⁵)
- 每行一条用例
- 示例：列表筛选有 4 个条件（对象类型/时间范围/方式/负责人）各 3 水平 → 全组合 81 条，用 L9(3⁴) 降到 9 条

**8. 错误推测法**
- 作为其他方法的补充，基于经验推测易错场景
- **每个功能点至少补 2 条**

### 错误推测常见方向

> 以下方向是常见易错场景，**不是穷举**，按功能点相关性选取：

| 方向 | 示例 |
|---|---|
| 空值/null 输入 | 必填项输入空字符串/null → 接口报错或前端拦截 |
| 超长字符串 | 文本输入超长内容 → 是否截断/报错 |
| 特殊字符 | 输入含 `<>&"'/\` → 是否转义、是否 XSS |
| 重复提交/快速连续点击 | 保存时连点保存按钮 → 是否生成重复记录 |
| 输入前后空格未 trim | 名称前后带空格 → 是否自动 trim |
| 输入框仅含空格 | 必填项仅输入空格 → 是否视为空值拦截 |
| 剪贴板粘贴 | 从 Excel 粘贴含隐藏字符/格式 → 是否清理 |
| 接口返回空导致兜底 | 列表接口返回空 → 是否展示兜底卡片/空状态 |
| 枚举值越界 | 类型字段传未配置的码值 → 是否报错 |
| 关联数据不存在 | 关联已删除的数据 → 是否报错或友好提示 |

### 方法与优先级的映射

设计用例时，**方法选用的场景特征**辅助判断优先级（与「优先级规则」四步流程叠加使用，不替代）：

| 方法产生的用例类型 | 倾向优先级 | 说明 |
|---|---|---|
| 场景法 — 基本流（主路径） | **P1** | 核心流程必经，阻塞场景 |
| 等价类 — 有效等价类正例 | **P2** | 正常业务场景 |
| 边界值 — 上点/内点 | **P2** | 正常范围内的重要功能 |
| 判定表 — 合法组合规则 | **P2** | 业务规则正例 |
| 状态迁移 — 合法转换 | **P2** | 正常状态流转 |
| 边界值 — 离点（min-1/max+1） | **P3/P4** | 边界外场景，按触发频率定 |
| 判定表 — 非法组合/异常规则 | **P3** | 异常但非极端 |
| 正交实验 — 代表性组合 | **P3** | 辅助覆盖组合场景 |
| 错误推测 — 空值/null/极端输入 | **P4** | 极端场景，极少触发 |
| 状态迁移 — 非法转换尝试 | **P3/P4** | 非法跳转，按影响定 |

> 这是**倾向**不是绝对——最终优先级以「优先级规则」四步判断流程为准，本表只辅助"看到某类用例时心里有数"。

### 横切维度清单（全面性第二层保障）

> 8 种方法从需求材料推导，保证「**需求内**不漏」；本清单与方法**正交**，是系统级维度——多数不写在需求里，但每次都存在，保证「**需求外**不漏」。生成阶段：每个功能点出完业务用例后逐维度过一遍；检查阶段：作为「用例生成后检查」第 5 项。

**强制三态判定**：每个功能点 × 每个维度，必须给出三态之一，**禁止静默跳过**——
- **已覆盖** → 标注对应用例编号
- **不适用** → 一句话理由（如"单端本地功能，无多设备同步"）
- **待确认** → 出泛化用例（预期写"按确认结论"）或在测试点标待确认。**需求没写 ≠ 维度不存在**——不臆测结论，但必须把维度摆出来

| # | 维度 | 自问问题 | 高危功能特征 |
|---|---|---|---|
| 1 | 多账号/多身份 | 同一功能对不同账号/身份表现一致吗？切换账号会串号吗？并登冲突吗？ | 权限、红点、缓存、购物车、草稿等账号绑定状态 |
| 2 | 多端/多设备 | 状态存服务端还是本地？A 端操作 B 端同步吗？ | 已读状态、消息、收藏、多端登录 |
| 3 | 聚合来源 | 展示位（tab 红点/角标数字/汇总行/总计数）聚合了**哪些**来源？来源清单不全则推导必错 | tab 红点、未读总数、统计汇总 |
| 4 | 时序与并发 | 数据到达与用户操作同时发生会怎样？重复触发收敛吗？批量风暴扛得住吗？ | 推送与点击竞态、连点、批量下发 |
| 5 | 异步/推送链路 | 在线推送与离线补拉两条链路都通吗？通知权限关闭/进程被杀时的兜底拉取？ | 消息推送、红点补显 |
| 6 | 状态持久化 | 重启/杀进程后状态对吗？本地缓存与服务端不一致时信谁？ | 已消状态复活、缓存脏数据 |
| 7 | 配置与开关 | 有白名单/开关/权限配置吗？用户**进出**配置前后状态残留吗？ | 白名单移除后残留、开关切换瞬间 |
| 8 | 存量回归 | 本需求触碰的代码/规则，会不会误改既有行为？ | 新展示规则 vs 存量规则共存 |
| 9 | 兼容与迁移 | 旧版本 App / 旧数据遇到新逻辑会怎样？ | 新消息结构对旧版、历史数据新展示 |
| 10 | 判定粒度 | 判定是账号级/企业级/部门级？粒度选错则同粒度内其他对象表现存疑 | 白名单按企业 Id、权限按角色 |

> 清单不是穷举，按功能点相关性选取；**发现新漏项必须沉淀回本清单**（错题本闭环，见「教训实例」）。

### 功能类型常规测试思路（按类型套用的检查清单）

> 与横切维度清单配合使用：横切维度是**系统级透镜**（多账号/多端/时序……），本节是**按功能类型**积累的常规思路（源自市面常见测试实践沉淀 + 教训实例）。一个功能点可命中多个类型（如"红点+推送"命中消息通知类），命中类型的检查项逐条三态判定（已覆盖/不适用/待确认），禁止静默跳过。新类型或新漏项沉淀回本表。

**类型未收录时的自拓展原则（强制）**：本表是不断生长的清单，**永远不可能穷举所有功能类型**。生成用例时对每个功能点必须自问："这个功能市面上常见吗？有没有通用测试经验？"——即使本表没有收录对应类型，也**必须自行拓展出常规测试用例**（参照同类功能的通用思路：该功能正常怎么用、哪里会出错、状态怎么流转、别人在这个功能上踩过什么坑），不能因为"清单里没有"就不出常规场景用例；拓展出的类型经确认有价值后沉淀回本表。

**消息通知 / 红点 / 角标类**：
- **消失时机语义**：清除触发是"点击"还是"进入即消"还是"停留时长"？秒进秒退、进入后杀进程算不算已读？——需求只写"点击"时必须与产品确认语义后固化
- **App 三态接收**：前台 / 后台 / 强杀（进程死亡）三种状态下推送的接收与展示——真实场景多发生在后台或强杀态，最易出错
- **送达 ≠ 展示**：通知权限开关、免打扰/专注模式、锁屏展示分别验证；区分 sent/delivered/presented/tapped 四个事件
- **实时性双链路**：在线推送实时亮起（不退出页面）与进入页面拉取补显，两条链路分别验证
- **多设备/多端同步**：红点/已读状态存服务端还是本地？A 端消除后 B 端是否还显示
- **账号切换串号**：退出换账号登录，上一账号的未读状态不得带给下一账号
- **聚合来源清单**：tab 红点/角标总数聚合了哪些来源？来源清单不全则联动推导必错——先与开发确认来源全集再固化预期
- **计数一致性**：角标数与真实未读数对账；"99+"封顶只是渲染决策，真实计数不丢
- **重复与风暴**：同一消息按 id 去重（不闪烁/不重复计数）；批量大量下发状态收敛
- **状态持久化**：已消除的状态重启不复活；跨会话为服务端状态而非会话状态
- **点击跳转**：深链目标页正确、冷启动携带参数、深链不被闪屏页吞掉
- **目标范围移除残留**：用户被移出白名单/回收权限后，已存在的红点/消息如何处理
- **旧版本兼容**：新消息结构/新红点类型对旧版本 App 的表现（不崩溃、降级展示）

**聊天 / IM 类**：
- 消息实时送达与乐观更新；时间戳、发送者名称正确
- 离线消息同步：重新打开后历史完整、无重复、顺序正确；断线重连后状态恢复
- 已读回执：单聊实时回显（秒级）、群聊已读人数、离线消息的已读时机、回执幂等
- 消息撤回：时间窗口内/外、单聊/群聊、撤回已读与未读消息的差异、多媒体撤回、无权撤回他人消息、撤回后占位提示、API 层数据彻底删除
- 消息删除/编辑在双方端的表现一致
- 多媒体消息：图片/视频/文件发送失败重试、大文件、EXIF 方向
- 正在输入提示的出现/消失时机；并发发送的消息顺序与去重

**支付 / 交易类**：
- 正向全流程：下单→支付→订单状态更新→通知→资金到账；逆向：取消、退款（全额/部分/多次累加不超额）、原路退回、区分"已受理"与"已完成"（异步终态）
- 金额边界：0 元、超大额、小数精度、支付金额与订单金额一致性、防篡改
- **幂等**：同一订单号只能成功支付一次（唯一约束）；连点支付按钮（前端置灰+后端幂等）；重复回调只入账一次
- 异常：弱网中断后状态一致；支付中途退出保持"待支付"；**第三方成功但本地失败**的对账补单（不二次扣款）；网关超时重试关联为一次操作；验签失败拒绝并记日志
- 对账：对账文件核对金额/状态/手续费；多扣少扣排查；资金流向验证
- 超时未支付自动关单、关单后再支付必须失败；加密传输、防重放、防越权（不能支付他人订单）、风控限流

**登录 / 注册 / 会话类**：
- 等价类+边界：正确/错误/空凭据、大小写敏感、前后空格 trim 归一化（注册与登录规则一致，否则账号"失联"）
- 密码长度边界**不静默截断**；错误提示不泄露"用户不存在"（防撞库枚举）；首次登录改密、忘记密码全链路、暴力破解锁定
- 验证码：时效内/外、刷新后旧码失效、重发倒计时置灰、错误次数上限、发送频控（同手机号/IP/设备）
- 多设备/并发登录策略：多端共存或互踢、设备数上限竞态不"超编"
- **Token 生命周期**：登出后旧 token 重放必须 401（客户端清 cookie 是"假登出"）；refresh token 失效与重复使用检测；改密后全部会话立即失效；空闲超时不被后台轮询"续命"
- 刷新风暴：access token 临期并发请求只触发一次 refresh；会话过期时正在填写的数据保留、重登后回到中断页

**列表查询类**：
- 分页边界（首页/末页/翻页中数据变更/跳页）、筛选条件组合与清空、空态、排序稳定性
- 刷新与加载更多的去重；大数据量与高并发加载表现
- 结果计数与实际一致（**计数本身会泄露数据存在性**，与权限类交叉）

**搜索类**：
- 输入：空输入、空格、单字符、超长文本、特殊字符/emoji、SQL/XSS 注入、回车提交、粘贴
- 搜索历史：记录去重、最新在前、上限条数、单条删除/一键清空+二次确认、跨端同步、退出登录清空（隐私）
- 热词/联想：触发防抖（300-500ms）、联想相关性、已下架/已删除内容不出现、键盘导航、点击回填并执行搜索
- 结果：相关度排序、计数准确、无结果引导、拼写容错、分页
- **竞态**：快速输入时旧请求结果覆盖新请求（须丢弃过期响应）；常见词 2 秒内出结果

**表单录入类**：
- 必填/格式/长度边界、重复提交防重、草稿暂存、编辑回显正确性、非法字符与 trim
- 确认字段不一致时在确认字段单独报错、不清空已输入内容；提交幂等

**导入 / 导出类**：
- 模板与格式校验：表头映射、编码（UTF-8 BOM/乱码）、分隔符、前导零被类型转换破坏、日期格式歧义
- **部分失败**：部分成功模式（有效行入库+行级错误报告含行号+可下载错误文件）与全量回滚模式（真事务、无孤儿数据）分别验证
- 重导幂等：按业务主键匹配，修正重传不重复导入已成功行
- 大数据量：流式处理内存平稳、异步任务+进度展示、文件/行数上限边界、导出无截断且行数与库一致
- 完整性：round-trip 无损（导出→导入→导出结果一致）
- 安全：公式注入（`=`,`+`,`-`,`@` 开头单元格在 Excel 打开不执行）、导出仅含有权数据、未认证拒绝

**权限控制类**：
- 判定粒度（账号/角色/企业级）、进出配置的前后状态残留、默认拒绝（fail closed）而非默认放行
- **水平越权**：篡改 URL/参数中的 ID 访问他人资源 → 403；读和写路径分别测（常见"读加固了、写遗漏了"）
- **垂直越权**：低角色调高角色接口 → **接口层 403**，而非仅前端隐藏按钮
- 批量操作：混选有权/无权记录 → 有权子集成功、其余明确报告
- 导出/搜索遵循同一权限：受限记录不出现在结果、也不出现在计数
- 字段级权限：敏感字段在接口响应中**不存在**而非仅前端隐藏
- 会话中间态：角色变更/成员移除后旧权限立即失效；越权用例在接口层验证

**文件上传 / 下载类**：
- 类型：白名单格式逐个验证、黑名单拒绝、**扩展名伪装**（exe 改 jpg 按文件头/MIME 校验）、特殊文件名（emoji/超长/换行符）
- 大小边界：0 字节拒绝、恰好上限接受、上限+1 客户端拦截不发请求
- 断点续传/分片：中途断网恢复后从断点续传（查已传分片清单只补缺失）、合并后 MD5 校验、弱网成功率、合并失败不误判为成功
- 异常：重复上传去重不静默覆盖、并发上传、取消上传干净中止无幽灵条目、未选文件不发请求
- 安全：路径穿越文件名（`../../`）、未认证 401/403、超频 429；下载：权限范围、文件名与内容一致

**报表 / 数据看板 / 统计类**：
- **数据准确性**：核心指标与源系统/独立 SQL 计算逐项比对——不只查总数，还要抽查明细
- **汇总一致性**：明细加总=页面总计、分部之和=总额（排查重复关联、去重逻辑、聚合层级错误）
- 时间范围：筛选边界日期（含头含尾规则）、跨月跨年、时区偏差；历史数据不被模型变更追溯改变
- 边界数据：金额 0、负数、空值、极端值的表现
- 图表：柱高/扇区比例与数据成比例、tooltip 悬浮精确值、图例/单位正确、筛选器联动所有图表
- 指标口径统一：同一指标跨看板算法一致；页面"1.25万"与导出 12500 一致
- 权限：多角色数据范围隔离、导出遵循相同权限

**App 专项（安装/升级/弱网/深链/分享）**：
- 安装：首次安装、覆盖安装（数据保留/登录态保持）、跨版本升级数据迁移、安装中断恢复、存储不足、签名不一致、多渠道
- 卸载：数据无残留（Android/data、公共目录、账号/历史）、二次卸载
- 升级：强更/非强更、下载中断断点续传、新增权限增量弹窗、跨多版本 N→N+M 迁移、升级后老数据兼容（**发版必回归真实数据覆盖升级**，用户无法降级）
- 弱网：各档位限速+丢包、请求竞态（旧响应覆盖新响应）、加载中控件禁用防闪退、超时按网络类型区分、断网恢复重试
- 深链：App 前台/后台/被杀/未安装四态 × 各入口（短信/邮件/浏览器/其他 App）；未登录→跳登录后回原目标页；畸形 URL 不崩溃；冷启动深链不被闪屏吞掉
- 前后台切换：回前台数据刷新、来电/切应用中断恢复
- 分享：各渠道内容完整性、分享回调、取消分享、未授权第三方登录
- 推送权限首次弹窗时机上下文化（首启即弹会被条件反射拒绝）

## 4. 格式规范

**默认风格：画布 2（按业务需求/迭代组织）**
- H2 需求标题以 `【模块名】` 开头
- 用户明确说"按功能模块全量沉淀"时才用画布 1 风格
- 元数据块**强制**：`> 优先级: P1/P2/P3/P4 | 关联需求: ... | 测试数据: ...`（优先级/关联需求/测试数据必填，`前置条件` 按需，知道接口时用 `调用的接口:` 写明）

**模块拆分原则**：见上方「Markdown 标题层级」章节的「模块按需拆分原则」三档表（简单不拆 / 中等拆模块 / 复杂拆模块+子模块），避免滥用。

**补充场景特有规则**（supplementer 用）：
- 不强制加 4 字段元数据块——若原 XMind 没用，补充时也不用
- 优先改写现有用例节点细节，少开新用例——新信息作为现有用例的子项追加
- 穷举类内容只列最有代表性的 2-3 个
- 保留内联代码块/配置块原样，不要"清理"

## 5. 用例生成后检查（生成 + 补充都必须执行）

每次生成或更新用例后，对最终 Markdown + XMind 执行一轮自检：

### 检查项
1. **内容正确性**：接口 URL/字段名/枚举值与需求快照一致，禁止臆测；覆盖需求所有分支；预期结果是"预期"而非操作步骤
2. **格式规范**：标题层级完整（H1迭代→H2需求→H3模块/用例→H4子模块/用例→H5用例），H2 需求必填；每个用例（带元数据块的标题，不管 H3/H4/H5）必须带元数据块（优先级/关联需求/测试数据必填，前置条件按需）；前置条件只写执行前需单独准备的业务前提（数据/造数准备、配置状态、业务逻辑依赖），不写通用背景类/动作状态类/具体值复述类废话、不捏造接口占位；若写前置条件且知道接口则含 `调用的接口:`；接口用例用中文名不加时间标记；用例标题是"动作 + 预期结果"完整句，无纯动作/名词短语式标题
3. **优先级合理性**：按四步判断逐条验证，禁止全量 P1 或全量 P3，必须分层
4. **测试点完整性**：逐条比对需求/设计稿，每个功能点/接口/业务规则都有对应用例覆盖；**不止比对需求字面——先理解需求真实意图与作用范围全集**：需求文字/产品稿只呈现改动的样例，不是验证范围全集，先结合知识库业务背景弄清需求究竟在做什么、作用于哪些对象的全集，再推导测试点（典型推导：改动作用于并列同类对象的全集如"往来对账权限控制"作用于全部六大往来模块页面而产品稿只画了部分、存量功能不被新逻辑误改、非目标人群/端对照、条件维度交叉组合格；并列同类对象的逐类验证不复制用例，验证范围写进 `前置条件:`（如"覆盖 待收款/待付款/…"）且测试数据支撑各类对象，只测单类对象即视为遗漏）；**材料涉及接口时功能用例 + 接口用例成对出现，不涉及接口时只出功能用例**；补充场景确认新设计引入的功能点全部有节点落地
5. **横切维度全面性**：按「测试设计方法」章节的「横切维度清单」对每个功能点**逐维度三态判定**——已覆盖（标对应用例编号）/ 不适用（一句话理由）/ 待确认（泛化用例或标注），**禁止静默跳过**；清单维度多数不写在需求里，"需求没写 ≠ 维度不存在"

- 自检发现问题 → 先修复、复检通过后再输出，并在最终回复里简短报告修了什么
